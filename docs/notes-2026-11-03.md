## 1. Saved words are not lost when a book is deleted

This was the premise of the request, and it turns out to be already handled —
but with three real defects around it.

### What already works

`saved_words.book_id` is declared:

    book_id INTEGER REFERENCES books(id) ON DELETE SET NULL

So deleting a book **keeps the word row** and blanks the link. It does not
cascade.

The preference `reader.word_memory_scope` defaults to `"library"`
(`BookSettings::load` in `src/pages/reader/book_settings.rs`). Under that scope,
`get_saved_words_for_scope` (`src/db/annotations.rs`) runs a `SELECT` over
`saved_words` with **no book filter at all**. An orphaned word — one whose
`book_id` is NULL — therefore still appears in the set, and still gets
underlined in every other book.

So the personal dictionary already survives book deletion in the default
configuration.

### The scope ladder (`get_saved_words_for_scope`)

| scope      | query                                                            | orphan visible? |
| ---------- | ---------------------------------------------------------------- | --------------- |
| `"off"`    | returns empty                                                    | no              |
| `"book"`   | `WHERE book_id = ?1`                                             | no              |
| `"series"` | `LEFT JOIN books`, `WHERE sw.book_id = ?1 OR b.series = ?2`; falls back to book scope when the book has no series | no |
| default    | no `WHERE` clause — every saved word                             | **yes**         |

### Defect 1 — the save toggle asks the wrong question

`saved_word_exists(word, book_id)` in `src/db/annotations.rs` runs:

    WHERE word = ?1 COLLATE NOCASE AND book_id = ?2

A NULL `book_id` never satisfies `book_id = ?2`, so an orphaned word **always
reports "not saved"**. The dictionary popover therefore offers to save a word
that is already in the dictionary, and saving it inserts a **second row**.

Nothing prevents the duplicate. The only index on the word column is
non-unique:

    CREATE INDEX IF NOT EXISTS idx_saved_words_word ON saved_words(word COLLATE NOCASE)

There is no `UNIQUE` constraint on `saved_words(word)`.

Callers of `saved_word_exists`: `src/pages/pdf_reader.rs` (two sites) and
`src/pages/reader/mod.rs` (three sites, including `ReaderMsg::ToggleSaveWord`).

### Defect 2 — the un-save path silently no-ops

`delete_saved_word_for(word, book_id)` in `src/db/annotations.rs` runs:

    DELETE FROM saved_words WHERE word = ?1 COLLATE NOCASE AND book_id = ?2

For an orphaned word this matches zero rows and returns `Ok`. The stroke
reports success and removes nothing.

### Defect 3 — visibility depends on scope

The same orphaned word is visible under `"library"` and invisible under
`"book"` or `"series"`. Same data, different answers, depending on a reader
setting.

### Related observations

- `saved_words_for_books(ids)` (`src/db/annotations.rs`) is documented
  *"words with no book are nobody's, so they cannot appear here"* — orphans are
  excluded by design. Callers: the author page and `src/service.rs`.
- The Saved Words page (`src/pages/saved_words.rs`) feeds itself from
  `list_saved_words("", None)`, which has **no book filter**. Orphans are
  already visible there.
- The book details page is the **only** place scoped to a single book:
  `src/service.rs` calls `get_saved_words_for_scope(book_id, "book")`. This is
  why removing the saved-words section from the book details page later would
  be a small, contained change.
- `src/pages/reader/lists.rs` filters on `word.book_id == Some(self.book_id)`
  in three places, including the undo (`Ctrl+Z`) capture path.

### The underlying design question

The code currently treats the book link two ways at once:

- as **provenance** — "where I met this word" (a label worth keeping and showing)
- as **ownership** — "this word belongs to this book" (used for matching,
  deletion, and filtering)

The clean resolution is to make it purely provenance: keep the column, display
it, but never let it decide identity, matching, or deletion.

### Columns not in the CREATE TABLE

`known`, `srs_interval`, `srs_ease`, `srs_due` are queried but absent from the
`saved_words` table definition. They are added by the helper
`add_column_if_missing(conn, table, column, ty)` in `src/db.rs` — that is this
project's column-migration mechanism, and it is the right tool if this work
needs a new column.

### "Dotted"

Unclear what is meant by a word being "dotted". There is already a two-state
`known` flag: `set_saved_word_known(id, bool)`, a `filter_known` toggle on the
Saved Words page, and a count rendered as `"{n} known · {total} word{s} saved"`.
If "dotted" means *marked as learned*, the machinery already exists.

## 2. Re-import: what is lost, and how big a fix is

### Already proven, mechanically

`src/db.rs` → `mod tests` → **`delete_and_reimport_loses_reading_data_known_gap`**

Seeds a book, sets a reading position + bookmark + highlight, hand-edits
title/description/rating, asserts all three reading artifacts exist **before**
the delete (so it cannot pass vacuously), deletes, re-imports the same hash,
calls `restore_overrides`, then asserts metadata came back and reading data did
not.

The test **pins current behaviour deliberately**. It is meant to fail the day
the gap is closed — invert the last block, do not delete the test to get back
to green.

CI-verified passing: run `41550784360` (by name in `test-full.txt`), and run
`41553179785` after a formatting fix — 1,132 passed / 0 failed, rustfmt diff
empty, clippy clean.

### The mechanism

`delete_book_single` calls `remember_overrides(id)`, then explicitly deletes
`book_content_fts`, `book_search_index_status`, `page_ocr_cache`, then `books`,
then `fs::remove_dir_all(book_dir(uuid))`.

Everything else dies by foreign-key cascade. **18 tables reference
`books(id)`**: 15 `ON DELETE CASCADE`, 3 `ON DELETE SET NULL` (`saved_words`,
`dict_lookups`, `comic_series`). Cascades genuinely fire because
`PRAGMA foreign_keys = ON` is set in **both** `Catalog::open` and
`Catalog::open_in_memory`.

`books.id` is `INTEGER PRIMARY KEY AUTOINCREMENT`, so a re-import gets a fresh
id and orphaned rows could not re-attach even if they survived.

`metadata_overrides` — keyed by `file_hash TEXT PRIMARY KEY` — is the **only**
file-hash-keyed table, and holds ten metadata fields plus a cover copied out to
`override_covers_dir()` (because the book directory is deleted).
`restore_overrides` re-applies those ten and prunes the stash row.

### Why the fix is small

Four things were verified specifically because each could have made this large:

1. **One import path covers every format.** Despite its name, `import_epub`
   (`src/epub.rs`) accepts `.epub`, `.cbz`, `.cbr` **and** `.pdf`. And
   `insert_book` has exactly **one** production caller — `import_epub`. So the
   single existing `restore_overrides` hook already sits on every import.
2. **Comics are covered for free.** `delete_comic_series` loops over the
   series' chapters calling `delete_book_single` on each, so every chapter is
   stashed individually.
3. **No migration needed for a new table.** `Catalog::open` runs its schema as
   one `execute_batch` of `CREATE TABLE IF NOT EXISTS` statements on **every**
   open. That is how `metadata_overrides` itself was added. The versioned
   migration block (`SCHEMA_VERSION = 22`, the `if v < 17` / `if v < 19`
   transforms) is only for *data* rewrites, not new tables.
4. **The capture hook already exists and is already fresh.**
   `remember_overrides` is called from `delete_book_single` *and* from roughly
   ten metadata mutators, so the stash is continuously up to date rather than
   written only at delete time.

### What to preserve vs let go

**Preserve** — cannot be rebuilt from the file:

- `reading_progress` — your place in the book
- `annotations` — highlights and notes
- `reading_bookmarks`
- `pdf_drawings` **and** `pdf_page_identities` (they must travel together)
- `patches`, `editor_snapshots`
- `shelf_books`, `reading_list` — organisation

**Let go:**

- `book_content_fts`, `book_search_index_status`, `page_ocr_cache` — rebuilt by
  re-indexing; costs time, not data
- `comic_chapters` — rebuilt by the import itself
- `book_tags` — already carried inside `metadata_overrides`
- `saved_words` — already survives via `ON DELETE SET NULL` (see §1)

**Judgment call, owner to decide:** `reading_events`, `reading_sessions`
(history and statistics).

### Tricky bits a fix must handle

- **Ordering.** `pdf_drawings` carries a composite foreign key
  `FOREIGN KEY (book_id, page_id) REFERENCES pdf_page_identities(book_id, page_id)
  ON DELETE CASCADE`. Page identities must be re-inserted **first** or the
  drawings are rejected.
- **Re-keying.** `restore_annotation(&Annotation)` and
  `restore_reading_bookmark(&ReadingBookmark)` already exist (used by the
  reader's undo-delete) but insert the row **verbatim**, including `row.id` and
  `row.book_id`. To restore onto a re-imported book the caller must overwrite
  `book_id` with the new id first. Both helpers call
  `sidecar::refresh_for_book` after inserting.
- **Id reuse.** `annotations`, `reading_bookmarks` and `pdf_drawings` have
  `AUTOINCREMENT` ids; `reading_progress` has a plain `INTEGER PRIMARY KEY`.
  Explicit-id re-insertion is safe for the former, needs thought for the latter.
- **The re-entrancy guard.** `remember_overrides` is protected by a `restoring`
  `AtomicBool` with a `RestoreGuard` that clears it on `Drop`. Any new
  reading-data restore must respect the same flag or it will re-stash what it
  is restoring.

### Why not fix the sidecar instead

`src/sidecar.rs` writes a per-book `kalam.json` and its `Sidecar` struct already
carries `progress_percent`, `reading_position`, `highlights`, `patches`,
`pdf_pages`, `pdf_drawings`. It looks like a ready-made answer. It is not:

- The `Sidecar` struct has **no bookmarks field at all**.
- `reading_position` is **deliberately stale**. `set_reading_progress` in
  `src/db.rs` carries the comment that refreshing the sidecar there is
  intentionally skipped because it runs on every page turn, and calls the exact
  place in a book *"the least valuable field in the backup"*.
- The file lives at `book_dir(uuid)/kalam.json` — **inside the directory
  `delete_book_single` removes**.
- `read_sidecar` has **no production caller**: only `sidecar.rs` itself and its
  own tests. Settings exposes only "Write missing copies" (`backfill_missing`).

So the sidecar is a half-built mechanism whose backup is deleted with the book
and never read back. Using it would mean reversing a deliberate decision and
relocating the file. Extending the existing `metadata_overrides` pattern is
smaller and cleaner.

### Size estimate

Roughly **150–250 lines** across three files:

- `src/db.rs` — one new table in the existing create batch (~15 lines)
- `src/db/metadata.rs` — extend `remember_overrides` and `restore_overrides`
- a new small module for the data shapes and capture/restore logic, to avoid
  growing `metadata.rs` further

Plus tests, including inverting the known-gap test above. **This is an
estimate, not a measurement** — nothing has been written.

`reader/engine.rs` (6), `reader/lists.rs` (3), `metadata_editor.rs` (2),
`reader/types.rs` (2), `series.rs` (2).

### The important pattern

**No page test constructs a GTK widget.** Grepping every page module's test
block for `gtk::init`, `Button::new`, `Label::new`, `Box::new` returned
nothing.

The existing tests are **decision-level**. Examples:

- `toc_rows_walk_parts_and_their_chapters_in_order`
- `toc_rows_fall_back_to_chapter_titles_only_when_nothing_has_a_target`
- `a_clean_import_reads_naturally`
- `restored_edits_are_called_out_but_only_when_there_were_some`
- `csv_escapes_commas_quotes_and_newlines`

They test plain functions that decide *what to show*, not the widgets that show
it.

### Why this is the right groundwork for a redesign

Widgets change in a redesign; decisions do not. A test asserting how the import
toast is worded survives any amount of visual churn. A test that clicks a
button does not.

So the pattern to follow: for each untested page, identify the decisions it
makes — filtering, ordering, grouping, empty states, formatting — extract them
into plain functions, and test those.

This is real work per page, and only worth doing for decisions the redesign
intends to keep. Start with the pages the redesign touches first, not all 36.

### A second layer already exists

CI captures screenshots per route (`docs/ci/screenshot.sh`, driven by
`KALAM_ROUTE`). That partly covers *"does the page render"*. It does not cover
*"does it decide correctly"* — which is exactly the gap decision-level tests
would fill. The two layers are complementary, not redundant.

Note also: synthetic pointer input is a dead end in CI (headless sway has no
libinput devices), so click-driven tests are not an option regardless.

## 4. Very large files, and the 2,943-line function

### Sizes measured on `main` @ `1a480b9`

`epub_editor.rs` 14,338 · `pdf_reader.rs` 12,731 · `comics_reader/mod.rs` 5,591 ·
`service.rs` 4,407 · `db.rs` 4,234 (larger on this branch after the new test) ·
`settings.rs` 3,760 · `app.rs` 2,895. `src/` totals 147,492 lines.

**EPUB editor: left alone** on the owner's word — "a future headache".

There is **no** file-size or function-length guardrail in `tests/guardrails.rs`.
The big-file rule is prose only, at `docs/WORKING.md`.

### The big function is a router, not an algorithm

`update_with_view` in `src/pages/pdf_reader.rs` (roughly lines 6828–9770) is
**2,943 lines**. Measured structure:

- a short guard block, then **one `match msg`**
- **171 arms**, covering 171 distinct `PdfReaderMsg` variants
- 2,913 of the 2,943 lines are inside arms
- **median arm: 11 lines**
- 352 `if`/`else` occurrences across the whole function

Largest arms:

| lines | arm |
| ----- | --- |
| 133 | `SelectionDragUpdate` |
| 113 | `UndoDelete` |
| 112 | `SelectionWordAt` |
| 112 | `PageRendered` |
| 101 | `DocumentLoaded` |
| 95 | `SelectionLineAt` |
| 63 | `PageTextReady` |
| 57 | `SelectionDragBegin` |
| 55 | `SelectionDragEnd` |
| 55 | `EscapeKey` |

The top ten total ~900 lines — about **30%** of the function.

It is long because the PDF reader handles a lot of messages, not because any
one thing is complicated.

### Recommendation

**Do not split all 171 arms.** That is a very large diff, changes no behaviour,
complicates the pending merge, and the redesign may reshuffle those messages
anyway.

The cheap, high-value move is extracting the **ten largest arms** into the
submodules that already exist — `pdf_reader/notes.rs`, `drawings.rs`,
`page_edit.rs`, `image.rs`, `pages_grid.rs`, `search_results.rs` are all
methods and free functions on the same model, reached via `use super::{...}`.
That leaves `update_with_view` around 2,000 lines for a fraction of the effort
and risk.

Alternatively do nothing now and split opportunistically when the redesign
touches it. Both are defensible. A full split *before* the redesign is the one
option worth arguing against.
