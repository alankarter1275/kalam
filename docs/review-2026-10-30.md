## A. Could actually bite you

**A1 — A web address is pasted into a shell command.**
`src/pages/remote_detail.rs:599` builds `xdg-open '<url>'` by string formatting
and hands it to the shell. A single quote inside the address breaks out and runs
whatever follows it. Not reachable today — no sources are registered and the
page is hidden — but it is one enabled feature away from being real.

**A2 — Importing an EPUB silently rewrites the book.**
The cleaner defaults to **on** (`src/epub_sanitizer.rs:43`, `.unwrap_or(true)`).
The `.orig` backup is gated on an unrelated metadata setting, so a book can be
rewritten with no copy kept.

**A3 — After cleaning, the fingerprint stops matching.**
Cleaning changes the file but never recomputes its hash, unlike the metadata
path at `epub_metadata.rs:456`, which calls `catalog.rehash_book`. Saved
overrides are keyed `ON CONFLICT(file_hash)`, so they quietly detach from the
book they belong to.

**A4 — PDF counts pages from 1, comics from 0, into the same column.**
Both write `reading_progress.chapter_index`. The percent formula at
`db.rs:1940` assumes 0-based, so PDF progress over-reports by about a page. No
crash — both call sites guard an empty chapter list. The visible damage is the
pace stat at `book.rs:1410`, which divides by a chapter count that is only
populated for EPUB (`service.rs:718`) and so silently falls back to the raw
index.

**A5 — Opening Kalam twice can produce "database is locked".**
No `busy_timeout` is set anywhere in `src/` or `crates/`, and there is no
single-instance guard.

**A6 — 179 CSS declarations GTK cannot parse.**
`resources/style.css` contains 153 `box-shadow`, 22 `filter` and 4
`transition: all`. GTK4's CSS parser rejects all three, so they do nothing at
all — the shadows the design asks for are not rendering — and each one emits a
warning at startup. Commit `93fa5254` had removed them; the rollback to
`de96a737` brought them back. That commit was separate from the Home and My
Library changes that prompted the rollback.

### B7 — decided: keep, because OPDS is coming

**Decision, 30 October 2026: `credential.rs` stays.** The owner plans to add
OPDS support later, and this is the machinery OPDS authenticates with.

The original finding called it dead code left behind by the removed `opds`
feature and recommended deleting it. **That was wrong.** It is unreachable
*from the app today* — no file under `src/` mentions it — but it is live,
compiled, tested API inside the engine:

- `chapbook-core/src/lib.rs` re-exports eight names from it.
- `chapbook-reader`'s public `SessionConfig` has a `credentials` field, a
  `with_credentials()` builder, and a `Debug` impl that names it.
- `chapbook-reader/src/open.rs:74` threads `&dyn CredentialStore` through the
  open path.
- `crates/chapbook-reader/tests/transport.rs` has three tests exercising it
  directly, all against an OPDS URL: a rejected credential being renewed and
  the open retrying **exactly once**; a store with nothing to offer surfacing
  the server's authentication document, because a shell needs it to build a
  login dialog; and a locked store not spending a retry, because *locked* is
  not *missing* and re-prompting is the shell's call.

### What keeping it does and does not preserve

Keeping `credential.rs` preserves the credential plumbing. It does **not**
preserve a working OPDS path — the rest was stripped, and
`docs/kalam/UPSTREAM.md` records exactly what and where:

| Removed for OPDS | Record |
|---|---|
| The `opds` and `ureq` cargo features, so there is no bundled HTTP client | `UPSTREAM.md:73` |
| The OPDS URL branch in `open.rs`'s library handshake | `UPSTREAM.md:84` |
| The `opds` subcommand in `tools/chapbook-cli` | `UPSTREAM.md:76` |

Line 73 also notes that a `[lints.rust] unexpected_cfgs` check-cfg entry was
added naming the removed features, so the `cfg` sites left behind in `src/` and
`tests/` stay warning-free rather than silently rotting. The seams are marked.

What OPDS will therefore need, when it is picked up: the transport feature
restored or a `HttpClient` implementation supplied by the app, and the
`open.rs` branch reinstated. The transport seam itself is intact —
`SessionConfig::with_transport(Arc<dyn HttpClient>)` — and there is already a
test asserting that a build with no bundled transport fails with a message
naming `with_transport`, which is a reasonable guardrail to have waiting.

**Consequence for A1.** The shell-injection fix in `src/pages/remote_detail.rs`
sits on this exact path. When it was reported it was called theoretical because
nothing could reach it. With OPDS planned, it stops being theoretical.

## D. Testing and CI

**D1 — CI photographs a layout the app does not use.**
`docs/ci/screenshot.sh` decides whether to shoot the windowed grid from the
*name of the output folder* — a heuristic left behind by a CI job deleted in
September 2026. The windowed grid became the app's default on 2026-09-04.
**Zero** of the 138 invocations in `ci.yml` set `WINDOWED` explicitly, so every
one falls through to the legacy grid and all 133 committed PNGs show a layout
nobody runs.

**D2 — The one visual check never actually checks.**
`docs/ci/check-shot.py` exists for a specific recurring bug: a book cover that
never loads, so the card draws a grey placeholder and stays that way. Its own
docstring puts it well — *"A human sees it instantly. CI sees a green build."*
It counts strongly-coloured pixels as a proxy, because the seeded covers are
deliberately saturated and placeholders are grey. But it **only prints numbers;
it never passes or fails.** The reasoning recorded in the file is sound — a
threshold invented on the spot is a guess, and a wrong threshold that fails a
good build is worse than none — but nobody came back to set the baseline. The
bug it was written for can still ship green.

**D3 — The screenshots job cannot fail a build.** It is `continue-on-error: true`
and not required for success. Only the `build` job can fail a run.

**D4 — `ci-logs/` commits are what destroyed the redesign.**
CI pushes to the branch after every run, so the branch is always moving and
always conflicts with `main`. Resolving that conflict on 29 October produced a
merge whose two parents were both `main`-side commits — main merged into main —
and that empty result was pushed over the real branch and merged as PR #17.
122,000 lines went with it. This is a live hazard, not history.

It reproduced in miniature on 30 October, on a pull request with nothing at
stake: CI pushed four commits to the working branch mid-session, one push was
rejected as a non-fast-forward, and the work had to be rebased over CI's own
commits to land.

### Why B3 cannot be implemented as decided

The decision was to move `ci-logs/` to CI artefacts. **That would blind every
future session, and it was verified rather than assumed.** From an agent
sandbox, on a completed run with seven artefacts attached:

- `gh run download` fails — artefacts are served from
  `productionresultssa11.blob.core.windows.net`
- `gh api .../actions/runs/<id>/logs` fails — logs are served from
  `results-receiver.actions.githubusercontent.com`

Neither host is reachable. Artefacts can be *listed* through `api.github.com`
but not *fetched*. Committed files are therefore the only channel by which CI
results reach an agent at all, which is why `ci-logs/` exists in the first
place. `ROADMAP.md`'s 2026-09-18 entry already said this — *"The PNG artifact
upload went to nobody — the sandbox cannot download artifacts"* — and it was
right.

Note that artefacts are not useless here: the `screenshots` job already uploads
six of them, and `publish-screenshots` downloads and merges them. That is
job-to-job transfer *inside* GitHub, which works fine. What does not work is
getting them out to a sandbox afterwards.

### What would actually solve D4

The goal behind the decision was to stop CI committing to the working branch.
That goal is achievable without losing readability: **have CI publish its log
commits to a dedicated branch** — say `ci-logs` — instead of to whichever
branch triggered the run. Then work branches never receive CI commits, so there
is nothing to race and nothing to conflict, and results stay readable with a
plain `git fetch origin ci-logs`.

This is a decision for the owner, because it replaces the one already made. It
is recorded here rather than implemented unilaterally.

**D6 — Five database modules have zero tests:** `shelves.rs` (793),

## E. The engine

**The engine is clean.** In 35,270 lines across 105 files, `crates/` contains
exactly three `#[allow(...)]` attributes — one `irrefutable_let_patterns`, one
`clippy::type_complexity`, one `clippy::too_many_arguments` — and zero
`#[allow(dead_code)]`. Every one of the 112 dead-code suppressions in this
project is in `src/`.

`UPSTREAM.md` already states the right thing: the crates are maintained in this
repository, there is no automatic upstream update process, and the archived

## What is worth saying about how this project works

The recurring pattern across nearly every finding above is the same one, and
`tests/guardrails.rs` already names it in its own header comment:

> Prose does not constrain anyone — least of all an agent.

The engine's archived `RESTRICTIONS.md` is the proof it cites: it banned `stylo`
while the workspace pinned five stylo crates, and mandated `lol_html` as the CSS
sanitizer when no such dependency existed. Two of its four rules were false and
nothing noticed, because nothing checked.

Every item on this list is a variant of that. A validator embedded in a markdown
code block that had to be copied out by hand. A screenshot check that reports
numbers but never fails. Four documents saying the editor was removed while it
was being built. A CSS comment as the only thing tying two colour palettes
together. A ratchet set 21 above its real value.

The mechanism that works is the one this project already invented: **count the
violations, assert the count cannot grow, and lower it as they get fixed.** That
is why `MAX_ARC_CATALOG_IN_PAGES` at 44/44 is the healthiest number in this
document, and why the loose ones are worth tightening rather than leaving.

The corollary for the work below: where a fix can be expressed as a guardrail
test, prefer that to a note in a document.
